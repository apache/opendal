# Deslopify

## Survey

Default to a read-only survey for simplification requests (including "look for another round") without modifying the working tree or creating report files. Read-only checks or temporary in-memory reproductions are fine when verifying a suspected bug, as long as the working tree remains untouched with no leftover files when the survey ends. Inspect the latest upstream `origin/main` commit (fetching when remote access is available) or the caller-specified target, reading the target tree via git without switching branches when it differs from the current checkout, and record the exact inspected short SHA. Check recent merges, relevant open PRs, and any review decisions the user supplied before reviving a proposal.

Because OpenDAL spans `core/core`, 50+ services, ~30 layers, transports/executors, integrations, and language bindings, anchor each survey to a cohesive slice rather than doing a shallow repo-wide pass. Use the caller-specified scope when provided; otherwise choose a focused slice (for example, `core/core` plus default core layers, one vertical operation path, a related group of layers, a cross-cutting boundary, or one binding) and look beyond the previous round's modules when evidence points elsewhere.

Step back from the local history that produced the code and read the target slice as a whole against `DESIGN.md` and `AGENTS.md` (especially *Optimizing for Reading*). Incremental changes often leave behind patchwork states, redundant glue, legacy shims, or misplaced abstractions that only look awkward from a global view. Aim for a cleaner mental model and less accidental complexity: both targeted cleanups and deeper redesigns are in scope when they remove real friction or reveal a stronger underlying invariant. Respect OpenDAL's preference for self-contained top-to-bottom local code—do not propose shared helpers or mode-flagged wrappers merely to deduplicate short local conditions, request parameters, or error mappings. Trace every candidate through real callers and observable tests, and skip purely cosmetic churn.

Useful starting lenses (not an exhaustive checklist):

- **Ownership and composition boundaries**: Check for drift against `DESIGN.md`—such as services caching HTTP transports or executors at build time instead of reading `&OperationContext`, context layers dropping forwarding to the previous resource, `raw` types leaking into public APIs, or leftover `*Accessor` names, `layer()` trampolines, `#[doc(hidden)] pub` service shells, and pass-through wrappers.
- **State machines and handle lifecycles**: Inspect public handles (`Reader`, `Writer`, `Lister`, `Deleter`, `Copier`, `Composer`) and internal `oio::*` or layer wrappers for loose booleans, `Option`s, and `debug_assert!`s that belong in payload-carrying enum states, or lifecycle leaks where `close()`, `abort()`, terminal failure, or drop can re-drive state or fabricate success.
- **Capabilities, validation, and simulation**: Check whether advertised `Capability` flags match actual guarantees, whether routing or forwarding layers revalidate arguments against the target service's capability, whether fallbacks in `SimulateLayer` or helpers violate semantic fidelity or predictable cost, and whether services retain unnecessary `enable_*` switches or obsolete upstream workarounds.
- **Guardrails and `unsafe` history**: Before simplifying `unsafe` code (such as binding FFI or compact metadata layout), defensive backend checks (such as HTTP 200 error-body parsing, range length checks, or checksum verification), or intentionally withheld capabilities, inspect the git and PR history of that exact code so real bug guardrails are not removed as boilerplate.
- **Tests and contract alignment**: Check whether tests protect real observable contracts rather than mirroring internal implementation details (bloated mock tests, dead fixtures, or tests that miss the path they claim to exercise), and check whether public rustdoc or `core/core/src/docs/specs/` has drifted from the implementation.

Open the report in the conversation with the inspected short SHA, the exact scope surveyed, and any round-specific focus or constraints. Rank the worthwhile findings, separating straightforward internal simplifications from broader design or public API proposals. For each finding, give the current code and call sites, concrete maintenance cost, proposed simplification or redesign, any public API or behavior impact, and the test or verification requirement that distinguishes a correct change (explicitly flagging service-specific behavior changes that require real-service verification). Cite exact file paths, line ranges, symbols, and relevant PRs or commits. Surface suspected correctness bugs separately and label what has been verified. An empty or short list is a valid result. End the survey after reporting it.

## Implement selected findings

When the maintainer selects items for a PR, carry those items and their review constraints forward. Use one reviewable commit per item in one PR by default, and follow the maintainer's direction if a finding belongs in a separate PR. Follow `AGENTS.md`, `DESIGN.md`, and `CONTRIBUTING.md`:

- **Real-service verification gate**: Do not modify service-specific protocol handling, response/error parsing, or external backend behavior based only on source analysis, mocks, or emulators. Reproduce and verify against the actual service (for example `OPENDAL_TEST=<service> cargo test behavior --features tests,services-<service>`); if real-service verification is unavailable, stop and report the block instead of substituting mocks.
- **Bug fixes and contracts**: Confirm any suspected bug with a focused regression test before presenting it as a fix. Update rustdoc or `core/core/src/docs/specs/` when observable behavior changes, and declare breaking changes in the PR template's `# Breaking changes` section rather than editing `CHANGELOG.md` for routine refactors.
- **Verification matched to the claim**: Run focused checks first (`cargo clippy --all-targets --features=... -- -D warnings`, targeted `cargo nextest run`), then broaden to match the blast radius (`cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo nextest run --workspace --no-fail-fast --all-features`, doc tests, `cargo fmt --all -- --check`, `taplo format --check`, `typos`, or the relevant binding/integration checks). Use Miri or sanitizers where `unsafe` ownership or aliasing paths are touched. For performance or layout claims, compare immediately before and after the relevant commit with the same target, toolchain, features, and workload.

Use `.github/pull_request_template.md` (including an accurate AI Usage Statement), record exact measurements, limits, and any skipped checks, and return the PR, commit list, and validation results for review.
