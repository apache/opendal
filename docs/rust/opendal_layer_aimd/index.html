§Apache OpenDAL™ AIMD Layer

AimdLayer adapts HTTP request rates to storage-service throttling. It combines an additive-increase/multiplicative-decrease controller with a token bucket for each of four independent categories: read (including stat), write (including copy, compose, create_dir, rename, and restore), delete, and list.

§Usage

Enable the facade feature layers-aimd and use opendal::layers::AimdLayer. With split crates, add opendal-layer-aimd alongside opendal-core:

use opendal_core::{Operator, Result};
use opendal_layer_aimd::AimdLayer;

fn configure(operator: Operator) -> Result<Operator> {
    let aimd = AimdLayer::builder()
        .max_rate(10.0)
        .initial_rate(2.0)
        .additive_increment(1.0)
        .burst(1)
        .build()?;

    Ok(operator.layer(aimd))
}

This example starts each category at 2 requests/s and grows by 1 request/s per active, unthrottled window up to 10 requests/s. A burst of 1 admits one request immediately. If you set only the rate bounds, the initial rate defaults to 2000 clamped to those bounds. Burst capacity and additive increment have independent defaults.

Add AIMD before retry so it observes each attempt’s errors. AIMD does not own retries, modify errors, or replace bandwidth and concurrency limits. Place a bandwidth throttle outside AIMD so locally generated RateLimited errors do not reduce the backend budget.

When using an HTTP concurrency limit, add ConcurrentLimitLayer first, then AimdLayer, then RetryLayer. Requests then wait for AIMD admission before acquiring an HTTP concurrency permit. To exclude this wait from HTTP latency metrics, also add the HTTP metrics layer before AIMD.

One layer represents one shared quota. Clones share the budgets and cooldown across operators. Build separate layers for separate accounts, credentials, or operation-specific quotas, and install them in the HTTP transports used by the corresponding requests. Each category receives its own configured rate and burst.

§Admission and feedback

The HTTP wrapper takes one token before forwarding each request with an OpenDAL Operation extension. Pages, multipart parts, and batch-delete requests each consume their own tokens. Response chunks and entries buffered from a page do not consume extra tokens. Requests without this extension, presigning, and non-HTTP I/O bypass admission. Requests hidden inside a custom transport, such as automatic retries or redirects, are outside this boundary.

Parsed ErrorKind::RateLimited errors observed by the service and I/O wrappers mark a feedback window as throttled. At the next window transition, its rate is multiplied by decrease_factor, bounded by min_rate. Otherwise, a window with HTTP responses adds additive_increment, bounded by max_rate. Empty windows do not change the rate. Defaults are 2000 requests/s initially, a range of 1–5000 requests/s, a one-second window, an increment of 300 requests/s, a multiplier of 0.5, and a burst of 100 requests per category.

HTTP completion and parsed errors occur at different boundaries. Feedback may be delayed until an operation propagates its error, and errors consumed by an inner layer are not visible. The controller uses the presence of a throttle signal, not a ratio of HTTP requests to operation errors. Other errors do not reduce the rate; an HTTP error response still establishes activity. A failed connection alone does not establish activity.

Feedback belongs to the enclosing storage operation’s budget. A composite operation may send requests in other categories, such as stat requests during a copy. Admission follows each request’s marker, while semantic feedback follows the enclosing operation; errors are not correlated with individual HTTP requests.

A marked HTTP 429 or 503 response with a usable Retry-After pauses new admissions across all four categories. The value may be a delay in seconds or an HTTP date. For an HTTP date, AIMD uses the response’s Date header when available and valid, and the local clock otherwise. An overlapping response can extend the deadline. AIMD returns each response as soon as it arrives and lets already admitted requests finish.

Waiters use a FIFO queue within each category, including when the cooldown ends. Cancelling a waiter removes its queue position without leaving token debt, and rate changes update pending waits. Buckets start full; only a request admitted to the next transport consumes a token. The layer does not spawn background tasks. Admission waits use the context executor. If the executor does not provide a timer, the layer uses Tokio and requires an active Tokio runtime with time enabled. Use with_sleep on the builder to override the timer with a function that accepts a Duration and returns a future completing after that duration. Rate calculations use the platform’s monotonic clock independently of the timer.

Services sign requests before transport admission. Bound operation duration when a queue could outlive the service’s signature validity period. Configure transport wrappers to forward to their inner transport, preserving this layer. This mechanism provides local adaptive pacing, not a distributed quota or a promise of fair sharing between processes.
