POSIX file system support.

§Capabilities

Depending on its configuration and the backing system, this service can expose:

  • create_dir
  • stat
  • read
  • write
  • delete
  • list
  • copy
  • rename
  • presign

Inspect the effective capability set with [opendal_core::Operator::info] and [opendal_core::OperatorInfo::capability] after building an operator.

§Read

Conditional reads compare if_modified_since and if_unmodified_since with the modification time reported by the opened file’s metadata, including subsecond precision when available. When both conditions are set, both must match.

§Write

With atomic_write_dir configured, unconditional writes with append(true) bypass staging and open the target file directly in append mode. Writes with if_not_exists(true) check for an existing destination when committing the staged file. If the destination exists, the write returns [opendal_core::ErrorKind::ConditionNotMatch] and preserves the existing file. This also applies when append(true) is set alongside if_not_exists(true).

On Linux, the conditional commit uses RENAME_NOREPLACE and returns [opendal_core::ErrorKind::Unsupported] when the kernel or filesystem lacks it. Other platforms publish the staged file through a hard link that atomically fails on an existing destination. The staging directory and the destination must be on the same filesystem. Without atomic_write_dir, conditional writes use exclusive file creation on all supported platforms.

§List

When set, start_after returns entries in lexicographic order and excludes paths at or before the marker in both non-recursive and recursive listings. Pass a path relative to the operator root, including the trailing / for a directory entry. Pass an empty marker to start a sorted listing from the beginning.

With start_after, the service reads and sorts each visited directory before yielding its entries. This can increase latency and memory usage for large directories. With start_after unset, the traversal follows the order of entries from the filesystem.

When glob is set, the service evaluates the pattern natively during directory traversal, entering leading literal directories directly and skipping subdirectories that cannot match. Discovered subdirectories that become unreadable or disappear during traversal are skipped, while errors on the starting and leading literal directories are returned.

§Delete

Recursive deletion targets the named filesystem entry. Deleting a/ recursively removes that directory and its descendants and leaves siblings such as ab/ intact. Use the trailing slash for portable directory deletion.

Deleting a symbolic link removes the link and preserves its target, even with recursive deletion enabled. Use a path without a trailing / to delete a dangling link.

A trailing / requires a directory target. A symbolic link to a file returns [opendal_core::ErrorKind::NotADirectory] when addressed this way. If the link target is missing, deletion through a directory path succeeds and leaves the link in place.

§Rename

On Linux, rename_with(...).if_not_exists(true) atomically moves the source only when the destination is absent. If the destination exists, the operation returns [opendal_core::ErrorKind::ConditionNotMatch] and preserves both files. The option requires kernel and filesystem support for RENAME_NOREPLACE. Otherwise, the operation returns [opendal_core::ErrorKind::Unsupported].

§Configuration

Use crate::FsConfig for serializable configuration and this builder’s methods for direct construction. The field and method documentation defines accepted values, defaults, and environment interaction.

§Direct I/O

Enable direct_io on Linux to bypass the kernel page cache for file reads and writes. The service handles the alignment of buffers, offsets, and lengths. Opening a file for direct I/O returns [opendal_core::ErrorKind::Unsupported] if the backing filesystem or file does not support it. copy still uses tokio::fs::copy. Append is unsupported when direct_io is enabled.

On Linux, finish all direct I/O before calling fork(). The service uses heap-allocated buffers, and running O_DIRECT operations concurrently with fork() can corrupt data.

§Example

§Via Builder

ⓘ
use std::sync::Arc;

use anyhow::Result;
use opendal::services::Fs;
use opendal::Operator;

#[tokio::main]
async fn main() -> Result<()> {
    // Create fs backend builder.
    let mut builder = Fs::default()
        // Set the root for fs, all operations will happen under this root.
        //
        // NOTE: the root must be absolute path.
        .root("/tmp");

    let op: Operator = Operator::new(builder)?;

    Ok(())
}
